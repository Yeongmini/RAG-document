# 모델 선택과 평가 기록

파이프라인 각 단계에서 **어떤 모델을 쓰는지**, **무엇과 비교했는지**, **왜 지금 모델을 골랐는지**를
개발 중 남긴 내부 실험 기록을 바탕으로 정리했습니다.

작성 원칙:

- 수치는 실험 기록과 결과 파일에 적힌 것만 옮겼습니다. 재지 않은 것은 **미측정**, 실험은 했지만 결과 파일이
  남아 있지 않은 것은 **기록 확인 필요**로 표시했습니다.
- 모든 수치는 **내부 실험**입니다. 표본이 작은 실험이 많아서 절마다 조건과 한계를 함께 적었습니다.
- 임베딩 모델(문장을 숫자 벡터로 바꿔 뜻이 가까운 것을 찾는 모델)과 생성 모델(글을 읽고 답을 쓰는 LLM)은
  하는 일이 달라서 따로 비교했습니다.
- 사양서 원문과 문서명은 싣지 않았습니다. 원본 코드·데이터·실험 파일은 회사 비공개 저장소에 있습니다.

## 1. 단계별 모델 — 현재 기본값

| 단계 | 하는 일 | 기본 모델 / 도구 |
|---|---|---|
| ① PDF 읽기 | 텍스트가 들어 있는 PDF를 문장 조각으로 정리 | PyMuPDF / pymupdf4llm (모델 아님, OCR 안 씀) |
| ② 값 추출 | 조각마다 "무엇 = 값" 카드를 뽑음 | `gemma4:26b-a4b-it-q4_K_M` |
| ③ 후보 고르기 | 카드와 검토 항목을 뜻·단위·값 모양으로 짝지음 | `KURE-v1` Q8 GGUF (1024차원), 유사도 하한 0.55, 카드당 후보 3개 |
| ④ 짝 검증·중재 | "이 값이 정말 이 항목의 값인가"를 읽고 판단 | `gemma4:26b-a4b-it-q4_K_M` |
| ⑤ 조문 검색 | 채워진 값에 관련 규칙 조문을 붙임 | `bge-m3` + FAISS (상위 5개) |
| ⑥ 판정 | 조문과 값을 대조해 적합 / 부적합 / 확인 필요 / 규정 없음 | `gemma4:26b-a4b-it-q4_K_M` |
| ⑦ 화면 표시 | 값과 근거 줄을 사양서 언어로 표시 | `gemma4:26b-a4b-it-q4_K_M` |

공통 실행 조건:

- 모델 서버는 Ollama 하나입니다. 기록된 환경은 로컬 GPU 1대입니다.
- LLM 호출은 전부 `temperature 0`, 추론 모드 끔, JSON 스키마로 출력 형식 강제입니다.
- 같은 입력은 판정·검증·카드 캐시에서 그대로 나옵니다. 재실행 결과가 같은 것은 캐시 덕분이고, 캐시 없는
  첫 실행에서는 경계에 걸린 판정 몇 개가 흔들릴 수 있습니다.

| 구분 | 내용 |
|---|---|
| **기본값 (운영 중)** | 생성 gemma4 26B-A4B Q4_K_M · 사양서 연결 임베딩 KURE-v1 Q8 · 조문 검색 임베딩 bge-m3 |
| **선택 기능** | 다중 경로 검색: 기본 검색이 정답 조항을 못 찾은 경우에만 보조로 추가 (기본 꺼짐) |
| **과거 실험 (채택 안 함)** | 임베딩: bge-m3·qwen3-embedding:4b (사양서 연결용) · 생성: qwen3.6, Qwen3.8-Flash-Next 176B-A6B · 수식 OCR: Qwen3-VL, glm-ocr |

## 2. 임베딩 모델 비교

### 2-1. 사양서 조각 ↔ 검토 항목 연결 — 3개 모델 비교 (2026-07)

**문제.** 사양서의 문장 조각이 검토 항목표의 어느 항목에 해당하는지 1차로 좁혀야 합니다. 이 단계에서
놓치면 뒤에서 LLM이 아무리 정확해도 값이 채워지지 않습니다.

| 항목 | 내용 |
|---|---|
| 비교 모델 | `bge-m3` · `KURE-v1` (Q8 GGUF) · `qwen3-embedding:4b` — 모두 Ollama |
| 데이터 | 영문 사양서 1종의 정리된 조각 1,752개 × 검토 항목 295개 |
| 정답 | 정답을 아는 조각→항목 짝 8건 |
| 지표 | 정답 항목의 순위(top-1/3/5 적중 수), 유사도 점수 분포, 임베딩 실패(NaN) 수 |
| 바꾼 것 | **모델만.** 같은 조각·같은 질의. 단, qwen3-embedding은 모델 권장 방식대로 질의 앞에 지시문을 붙임 |

**결과.** KURE-v1과 bge-m3가 정확도 공동 1위였고, KURE-v1이 임베딩 실패가 더 적었습니다.
qwen3-embedding:4b는 지시문을 붙여도 뒤졌습니다.

**세부 수치: 기록 확인 필요.** 비교 스크립트가 결과를 화면에만 출력해서 모델별 적중 수와 실패 수는 결과 파일로
남아 있지 않습니다.

**KURE-v1을 고른 이유.**

1. 정확도가 bge-m3와 같았고, 임베딩 실패가 적어 더 안정적이었습니다.
2. 한국어 특화 모델이라 국문 사양서에도 쓸 수 있습니다(비교 자체는 영문 1종으로 함).

**함께 확인된 사실 (모델 선택보다 중요했던 것).**

- 세 모델 모두 유사도가 0.5~0.65에 몰려, 점수 하나로 맞는 짝과 틀린 짝을 가를 수 없었습니다. 그래서
  **뒤에 LLM 검증 단계를 반드시 두는 구조**로 정했습니다.
- 양자화된 임베딩 모델은 특정 기호(따옴표, 괄호 든 질의 등)가 들어간 텍스트에서 NaN을 내고, 그러면 배치 전체가
  실패합니다. 실패하면 한 개씩 다시 보내고, 끝까지 안 되는 텍스트는 따로 처리합니다.

**남은 한계.**

- 정답 짝 8건, 영문 1종으로 표본이 매우 작습니다.
- 이후 실제 조선소 사양서 3종을 진단했더니, 규칙 관련 사실의 47%는 상위 3개 후보가 모두 틀렸고 17%는
  유사도 하한 미만이라 후보가 하나도 붙지 않았습니다. 지금 시스템의 가장 큰 병목입니다. 다만 해결 방향은 모델
  교체가 아니라 후보 수와 어휘 보강입니다(4-2절).
- 그 뒤로 다른 임베딩 모델과 다시 비교한 적은 없습니다.

### 2-2. 규칙 조문 검색 — bge-m3 고정 (비교하지 않음)

| 항목 | 내용 |
|---|---|
| 모델 | `bge-m3` |
| 고른 이유 | 조문 검색 DB는 외부에서 bge-m3로 구축된 것을 받아 썼습니다. 질의 벡터는 DB와 같은 모델로 만들어야 하므로 **선택이 아니라 제약**입니다 |
| 확인한 것 | 로컬 bge-m3로 DB 벡터를 다시 계산하면 원본과 유사도 0.9999로 일치 (작업 기록, 검증 로그 파일은 기록 확인 필요) |
| 다른 모델 비교 | **미측정.** DB를 다시 만들어야 해서 시도하지 않음 |

## 3. 생성 모델(LLM) 비교

### 3-1. gemma4 26B-A4B vs Qwen3.8-Flash-Next 176B-A6B — 추출·검증·판정 전체 (2026-09)

**문제.** 실제 조선소 사양서에서 채움률이 34~38%에 머물렀습니다. 더 큰 모델로 바꾸면 나아지는지 확인했습니다.

| 항목 | gemma4 (현행) | Qwen3.8 (비교) |
|---|---|---|
| 모델 크기 | 총 25.8B, 활성 4B (MoE) | 총 176B, 활성 6B (MoE) |
| 양자화 | Q4_K_M (4비트) | W4A16 AutoRound (가중치 4비트) |
| 모델 서버 | Ollama | vLLM + Ollama 형식을 흉내 내는 중계 프록시 (JSON 스키마를 vLLM 형식으로 변환) |
| 데이터 | 실제 조선소 사양서 1종(벌크선), 사람이 만든 정답표 22건 | 같음 |
| 파이프라인 코드 | 그대로 | 그대로 (모델 호출 주소만 바꾼 사본) |
| 캐시 | 기존 결과 기준 (같은 날 다시 돌린 것 아님) | 캐시를 전부 비우고 처음부터 실행 |

**결과.**

| 지표 | gemma4 | Qwen3.8 |
|---|--:|--:|
| 추출한 사실 | 567 | 512 |
| 검증 통과(채움) | 84 | 69 |
| 채움 항목 | 64 | 60 |
| 규칙 관련 사실 채움률 (키워드로 추정한 분모) | 35% | 38% |
| 판정 행 | 39 | 36 |
| 적합 / 부적합 / 확인 필요 | 20 / 0 / 19 | 17 / 0 / 19 |
| **정답표 22건 (추출)** | **20개 맞음 · 틀림 0** | **17개 맞음 · 틀림 0 · 3개 못 채움** |
| 처리 시간 (캐시 없음, 4개 동시) | 미측정 | 21.5분 (LLM 호출 936회) |
| 메모리 | 미측정 | 미측정 |

**해석.**

- 두 모델이 함께 판정한 31개 중 3개가 갈렸습니다. 전부 gemma4는 적합, Qwen은 확인 필요였습니다. Qwen이 조문을
  더 문자 그대로 읽었습니다. 틀린 답(근거 없는 적합/부적합)은 양쪽 모두 0건이었습니다.
- Qwen이 못 채운 3건 중 1건은 추출 단계에서 표 행의 주어를 잘못 붙인 것을 검증기가 정당하게 거부한 경우였습니다.
  큰 모델도 표 맥락을 붙이는 데서 실수했습니다.
- 부수 관찰: Qwen은 영어 프롬프트에서는 "30 이상"에 30이 포함되는 경계값을 맞게 판정했지만, 한국어 프롬프트에서는
  3번 중 3번 틀렸습니다. 언어에 따라 판정이 갈리는 모델은 국문 사양서에 위험합니다.

**결론: 교체하지 않음.** 채움은 비슷했고, 정답표 기준으로 3건 뒤졌고, 판정은 더 보수적이었고, 더 느렸습니다.
병목은 모델 크기가 아니라 후보 고르기라는 앞선 진단과도 맞습니다. 재검토 조건은 "속도 회복 + 3척 이상에서 정답표
우위 확인"으로 정했습니다.

**이 비교의 한계.**

- 모델만 바꾼 실험이 아닙니다. 모델 서버(Ollama ↔ vLLM), 양자화 방식, 캐시 조건이 함께 달랐습니다.
- 문서 1종, 정답 22건입니다.
- gemma4의 같은 조건 처리 시간과 두 모델의 메모리 사용량은 재지 않았습니다.

### 3-2. qwen3.6 vs gemma4 — 값 추출 단계 (2026-07, 초기)

| 항목 | 내용 |
|---|---|
| 기록 | 같은 GPU에서 qwen3.6은 초당 5토큰(조각 929줄에 약 6시간), gemma4는 초당 30토큰(약 1.5시간) |
| 측정 지표 | 처리 속도 (코드 주석에 남은 관찰값. 원본 로그 없음) |
| 품질 비교 | **기록 확인 필요** — 비교했다는 언급만 있고 수치는 없음 |
| qwen3.6 버전·양자화 | **기록 확인 필요** |
| 바꾼 것 | 모델과 함께 **방식도 바뀜.** "항목마다 값을 찾아라"에서 "줄마다 무엇의 값인지 읽어라"로 전환한 시기라, 모델만 비교한 실험으로 보기 어려움 |

### 3-3. LLM 검증 단계가 필요한가 — 임베딩만 쓸 때와 비교 (2026-07)

모델끼리 비교한 것이 아니라 **구조 비교**입니다. 임베딩 유사도와 단위 필터만으로 값을 채우면, 사양서에 없는 값
자리에 단위만 같은 엉뚱한 숫자가 여러 항목에 붙었습니다. gemma4가 후보를 읽고 판단하게 하자 이런 가짜 후보를
거부했습니다. 기록된 속도는 GPU에서 항목당 약 1초입니다. 거부 정확도 같은 정량 지표는 **기록 확인 필요**입니다.

이때 정한 규칙:

- 출력은 엄격한 JSON 스키마로 강제합니다. 자유 서술 칸을 넣으면 길이 제한에 잘려 JSON이 깨졌습니다.
- 임베딩 모델과 LLM을 번갈아 부르면 모델을 바꿔 올리느라 느려집니다. 그래서 벡터는 미리 계산해 파일로 저장해 둡니다.

### 3-4. 수식 OCR — 규칙 PDF 전처리 (2026-07, 과거 작업)

- 규칙 PDF의 수식 이미지를 글자로 바꾸는 데 gemma4와 Qwen3-VL을 비교했습니다. 수식 1건에서 둘 다 복원했고
  gemma4 출력이 더 깔끔했습니다.
- gemma4가 추론 모델로 바뀐 뒤 추론 모드를 끄지 않아서, 이미지 45장 중 42장이 빈 결과였는데도 로그에는 성공으로
  찍혔습니다. qwen3.6도 같았습니다. 지금 모든 LLM 호출에서 추론 모드를 끄는 이유입니다.
- 판정 기준값이 될 숫자는 두 모델(gemma4 / glm-ocr)로 교차 확인하기로 했습니다. 기록상 한글은 gemma4, 순수 수식은
  glm-ocr이 강했습니다(정성 평가, 수치 없음).

사양서 쪽은 텍스트가 들어 있는 PDF만 받으므로 지금은 OCR을 쓰지 않습니다.

## 4. 검색 방식 비교 (모델은 그대로, 방식만 바꿈)

### 4-1. 조문 검색: 벡터 / BM25 / 하이브리드

| 항목 | 내용 |
|---|---|
| 표본 | 인계 레코드 1,003건, 조문 조각 631개, 후보 폭 상위 20개 |
| 정답 | 검토 항목표에 적힌 근거 조항 — 채점에만 쓰고 검색 입력으로는 쓰지 않음 |
| 바꾼 것 | 검색 방식만 (임베딩은 bge-m3 그대로) |

| 방식 | hit@1 | hit@3 | hit@5 | MRR |
|---|--:|--:|--:|--:|
| 벡터 검색 (bge-m3, **현행**) | 64.7% | 85.6% | 88.4% | 0.757 |
| BM25 (단어 일치) | 73.5% | 90.2% | 91.6% | 0.813 |
| 하이브리드 (벡터 + BM25, RRF로 순위 합침) | 77.8% | 89.0% | 93.6% | 0.843 |

(hit@k: 정답 조항이 상위 k개 안에 들어온 비율. MRR: 정답 순위의 역수 평균.)

**기본값으로 올리지 않은 이유.** 주 검색을 통째로 바꾸면 검색되는 조문이 달라져서, 사람이 이미 확인한 판정까지
흔들렸습니다. 그래서 기본은 벡터 검색으로 두고, 기본 검색이 정답 조항을 못 찾은 경우에만 다중 경로 검색을
보조로 쓰게 했습니다. 보조 모드에서 판정이 뒤집힌 건은 0건으로 기록돼 있지만, 결과 파일은 **기록 확인 필요**입니다.

### 4-2. 사양서 후보 고르기: 후보 확대 + 어휘 융합 (2026-09, 격리 실험)

| 항목 | 현행 | 실험 |
|---|--:|--:|
| 설정 | 후보 3개, 임베딩만 | 후보 8개 + 항목 이름·별칭 단어 일치 점수 가중(0.12) |
| 검증한 짝 | 658 | 1,258 (+91%) |
| 채움 항목 | 64 | 74 |
| 규칙 관련 사실 채움 | 35/101 (35%) | 40/101 (40%) |

조건은 실제 조선소 사양서 1종의 격리 사본이고, 임베딩은 KURE-v1 그대로, LLM 검증 시간은 약 2배였습니다.
후보를 넓히자 엉뚱한 값이 전용 항목에 채워져 판정이 부적합으로 바뀐 **정밀도 사고 1건**이 나왔습니다.
그래서 적용 조건 검사(조건이 사양서에 없으면 '확인 필요'로 고정)를 먼저 넣기 전에는 본선에 반영하지 않습니다.

## 5. 현재 선택 요약과 남은 한계

| 역할 | 선택 | 핵심 이유 | 근거 수준 |
|---|---|---|---|
| 생성 (추출·검증·판정) | gemma4 26B-A4B Q4_K_M | 176B 모델보다 정답표 우위(22건 중 20 vs 17), 틀린 답 0, 활성 파라미터가 작아 빠름 | 문서 1종 비교 |
| 임베딩 (사양서 연결) | KURE-v1 Q8 | bge-m3와 정확도 공동 1위, 임베딩 실패가 더 적음, 한국어 특화 | 정답 8건 비교, 세부 수치 미보관 |
| 임베딩 (조문 검색) | bge-m3 | 제공받은 조문 DB와 같은 모델이어야 함 | 제약 (비교 없음) |
| 조문 검색 방식 | 벡터 검색 (다중 경로 검색은 보조) | 하이브리드가 hit@5 +5.2%p였지만 확인된 판정이 흔들리지 않게 보조로만 사용 | 1,003건 평가 |

**남은 한계**

1. 생성 모델 비교는 문서 1종, 사양서 연결 임베딩 비교는 정답 8건으로 표본이 작습니다.
2. 실제 사양서 채움률이 34~38%입니다. 병목은 모델이 아니라 후보 고르기 단계입니다.
3. 판정 캐시 키에 모델명이 없습니다. 모델을 바꾸면 옛 모델의 판정이 캐시에서 그대로 나오므로, 다음 비교 전에 고쳐야 합니다.
4. 캐시 없이 처음 돌리면 경계에 걸린 판정 몇 개가 흔들립니다. 운영 재현성은 캐시에 기대고 있습니다.
5. 처리 시간과 메모리를 모델별로 같은 조건에서 잰 기록이 없습니다.
