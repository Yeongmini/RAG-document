# 건조사양서 자동 검토 — 규칙 대조 RAG 파이프라인

> 선박 건조사양서 PDF의 값을 국제 선박 규칙 조문과 대조해, 항목별로 **적합 / 부적합 / 확인 필요 / 규정 없음**과
> 근거 조항을 내는 로컬 LLM 파이프라인입니다.
> 사내 프로젝트라 소스 코드와 데이터는 비공개이고, 이 저장소에는 **설계·기술 선택 과정·평가 요약**만 정리했습니다.

---

## 한눈에 보기

| | |
|---|---|
| 문제 | 건조사양서에 적힌 값을 사람이 규칙 조문(IGF Code 등 저인화점연료 선박 규칙)과 하나씩 대조해야 하는 검토 작업 |
| 접근 | 규칙에서 검토 항목을 먼저 정하고 → 사양서의 줄마다 "무엇 = 값"을 읽어 항목에 채운 뒤 → 항목별로 고정된 근거 조항과 대조해 판정 |
| 모델 | 로컬 Ollama 위의 생성 모델 1개 + 임베딩 모델 2개. 외부 API로 데이터가 나가지 않음 |
| 내부 측정 결과 | 연습용 사양서 10종: 사람이 확인한 채움 정답 135개 전부 일치 · 조문 검색 hit@5 88.4% (1,003건) |
| 알려진 한계 | 실제 조선소 사양서 3종에서 규칙 관련 사실 채움 34~38% — 병목은 후보 고르기 단계 |
| 기간 | 2026년 6월 ~ 10월 (저장소 기록 기준) |

## 내 역할

**분석 엔진(사양서 PDF → 판정 결과)의 설계와 구현을 맡았습니다.**

- **파이프라인 설계·구현**: 사양서 파싱 → 값 추출 → 검토 항목 짝짓기·검증 → 조문 검색·판정 전 단계
- **검토 항목표 설계**: 규칙 PDF를 조문 단위로 나누고, 규칙이 요구하는 확인 항목과 근거 조항을 정의.
  항목표는 직접 고치지 않고 변경 스크립트로만 갱신하도록 버전 관리
- **모델·검색 실험**: 임베딩 3종, 생성 모델 비교, 조문 검색 방식 평가 ([모델 선택과 근거](#모델-선택과-근거))
- **품질 관리**: 회귀 방지 장치 4종 구축, 사람이 검수한 결과를 정답표·판정 스냅샷으로 고정, 실제 사양서 성능 진단
- **검토 화면 프로토타입**: 판정 결과를 누르면 원문 위치를 형광펜으로 표시, 영문 판정 결과를 사양서 언어로 표시

팀원이 맡은 부분: 분석 엔진을 감싸는 API 서버·컨테이너 배포, 사용자용 웹 서비스(화면·이력 DB).
규칙 조문 검색 DB는 외부에서 받아 썼습니다.

---

## 동작 방식

```
[규칙 쪽]    규칙 PDF ─→ 조문 단위로 나눔 ─→ 검토 항목표 (확인할 항목 목록, 항목마다 근거 조항 고정)
                              └─→ 조문 검색 DB (bge-m3 벡터 + 조문 메타)

[사양서 쪽]  사양서 PDF ─읽기→ 문장 조각
             ─후보 고르기(뜻 벡터 + 단위 + 단어 겹침)→ ─LLM→ "무엇 = 값" 카드
             ─유사도·단위·값 모양 확인→ 후보 짝 ─LLM 검증→ 검토 항목표에 값 채움 (+원문 위치 기억)

[판정]      채워진 값마다 고정 근거 조항 + 그 조항이 가리키는 참조 조문(1단계)을 붙임
             ─LLM→ 적합 / 부적합 / 확인 필요 / 규정 없음 + 근거 조항 번호 + 사유
```

웹 화면에서 판정 결과를 누르면 사양서 원문에서 그 값이 있던 자리가 형광펜으로 표시됩니다.

## 핵심 설계 결정

| 결정 | 이유 |
|---|---|
| **검토 항목표를 먼저 만든다** | 사양서에서 아무 값이나 뽑지 않고, 규칙이 요구하는 항목을 먼저 정해 두고 그 값을 찾아옵니다 |
| **"이 항목의 값을 찾아라" 대신 "이 줄은 무엇의 값인가"** | 항목을 주고 값을 찾게 하면 LLM이 없는 답을 억지로 만들었습니다. 줄마다 무엇의 값인지 읽게 하면 모델이 항목표를 모르므로 끼워 맞출 수가 없습니다 |
| **항목 → 근거 조항 대응은 고정** | 어느 조항이 어느 요구사항을 다루는지는 규칙이 정한 사실이라 실행 중에 추측하지 않습니다. LLM이 조항 번호를 지어내는 환각이 구조적으로 막힙니다 |
| **값의 모양은 코드로 검사** | 단위·숫자 형식·허용값 검사는 LLM이 아니라 코드가 맡고, LLM은 "같은 대상을 말하는가"만 판단합니다 |
| **판정은 네 갈래** | "적합"은 조문에 요건이 있고 값이 만족할 때만 씁니다. 조문이 요구하지 않는 항목은 "규정 없음"으로 분리해 거짓 안심을 막습니다 |
| **"확인 필요"는 실패가 아니다** | 배치도·계산서를 봐야 하거나 사양서에 값이 없는 항목을 사람 몫으로 정확히 넘기는 것이 목표입니다. 설계 구성값은 원문에 없으면 추론하지 않고 "확인 필요"로 둡니다 |
| **재현성은 캐시로 보장** | 같은 입력은 판정 캐시에서 그대로 나오게 해서, 같은 문서를 다시 분석해도 결과가 같습니다 |

## 모델 선택과 근거

생성 모델과 임베딩 모델은 하는 일이 달라서 역할별로 따로 비교했습니다. 아래 수치는 모두 **내부 실험**이며,
조건·한계·미측정 항목은 **[docs/model-evaluation.md](docs/model-evaluation.md)** 에 정리했습니다.

| 역할 | 현재 모델 | 비교한 대안 | 결과 요약 |
|---|---|---|---|
| 값 추출·검증·판정 (생성) | `gemma4:26b-a4b-it-q4_K_M` (총 25.8B, 활성 4B MoE, 4비트) | Qwen3.8-Flash-Next 176B-A6B (W4A16) | 실제 사양서 1종, 정답 22건: **20개 맞음 vs 17개 맞음·3개 못 채움**, 틀린 답은 양쪽 0건 |
| 사양서 조각 ↔ 검토 항목 연결 (임베딩) | `KURE-v1` Q8 (1024차원) | bge-m3, qwen3-embedding:4b | 조각 1,752 × 항목 295, 정답 짝 8건: **bge-m3와 공동 1위, 임베딩 실패가 더 적음**, qwen3-embedding 열세 |
| 규칙 조문 검색 (임베딩) | `bge-m3` | — (비교 안 함) | 외부에서 받은 조문 DB가 bge-m3 벡터라 같은 모델이 필수 |
| 조문 검색 방식 (모델 아님) | 벡터 검색 | BM25, 하이브리드 | 1,003건 hit@5: 벡터 88.4% / 하이브리드 93.6% — 기본값은 유지하고 보조로만 사용 |

**선택 이유**

- **생성 모델은 크기보다 정확도와 속도.** 총 파라미터가 약 7배인 모델로 바꿔도 채움은 비슷했고, 정답은
  3건 덜 맞혔고, 더 느렸습니다. 병목이 모델이 아니라 후보 고르기 단계라는 진단과도 맞아 교체하지 않았습니다.
- **임베딩은 점수보다 안정성.** 정확도가 같으면 임베딩 실패(NaN)가 적은 쪽을 골랐습니다. 세 모델 모두
  유사도가 0.5~0.65에 몰려 맞는 짝과 틀린 짝을 가를 수 없어서, 뒤에 LLM 검증 단계를 반드시 둡니다.
- **출력은 형식으로 묶는다.** 모든 LLM 호출은 `temperature 0`, 추론 모드 끔, JSON 스키마 강제입니다.

**남은 과제**: 비교 표본이 작습니다(문서 1종, 정답 8건). 처리 시간과 메모리를 모델별로 같은 조건에서 잰
기록이 없습니다. 판정 캐시 키에 모델명이 없어 다음 비교 전에 고쳐야 합니다.

## 결과와 한계 (내부 측정)

| 항목 | 결과 | 조건 |
|---|---|---|
| 채움 정확도 (연습용 사양서) | 사람이 확인한 정답 135개 전부 일치 | 연습용 사양서 10종, 2026-08 재채점 |
| 조문 검색 | hit@5 88.4%, MRR 0.757 | 인계 레코드 1,003건, 정답은 채점에만 사용 |
| 실제 사양서 채움 | 규칙 관련 사실의 34~38% | 실제 조선소 사양서 3종 진단 (2026-09) |
| 개선 실험 | 35% → 40% | 후보 수 확대 + 단어 일치 점수 융합, 1종 격리 실험 (본선 미반영) |
| 처리 시간 | 처음 보는 문서 약 20분, 한 번 처리한 문서 수 분 | 운영 중 관찰값 (정식 측정 아님) |

- 연습용 사양서는 검토 항목에 맞춰 작성된 문서라 라벨이 항목 어휘와 비슷합니다. 실제 사양서와의 성능 차이가
  여기서 생기며, 이를 직접 진단해 병목을 후보 고르기 단계로 특정했습니다.
- 실패할 때는 오판이 아니라 "확인 필요"가 늘어나는 방향(안전한 쪽)입니다. 다만 후보를 넓히는 실험에서
  잘못 채운 값이 부적합 판정으로 이어진 사례가 1건 나와서, 적용 조건 검사를 먼저 넣기 전에는 반영하지 않았습니다.
- 캐시 없이 처음 돌리면 경계에 걸린 판정 두세 개가 흔들립니다. 운영 재현성은 캐시에 기대고 있습니다.

## 회귀 방지 장치

"고쳤더니 다른 게 조용히 망가지는" 사고를 막으려고 결과를 고정해 두는 장치 네 가지를 두었습니다.

| 장치 | 지키는 것 |
|---|---|
| 파서 고정 테스트 | 사양서를 읽은 결과가 바뀌지 않았는지 |
| 검토 항목표 검사기 | 항목표 구조가 깨지지 않았는지 (위반 0건이어야 통과) |
| 채움 정답표 | 사람이 확인한 정답 값이 그대로인지 |
| 판정 스냅샷 | 사람이 확인한 판정이 뒤집히지 않았는지 |

수정은 기준 문서 1종으로 먼저 검증하고, 확정된 뒤에만 전체 문서를 다시 채점합니다(10종 약 70분).

## 개발하며 배운 것

- **임베딩 유사도만으로는 값을 채울 수 없다.** 점수가 좁은 범위에 몰려, 단위만 같은 엉뚱한 숫자가 여러 항목에
  붙었습니다. 검증 단계를 LLM에 맡기고, 값의 모양 검사는 코드로 분리했습니다.
- **추론 모델은 조용히 빈 답을 낸다.** 모델이 추론(thinking) 모드로 바뀐 뒤 출력 길이 제한 안에서 최종 답을
  못 내 빈 결과가 "성공"으로 기록됐습니다. 이후 모든 호출에서 추론 모드를 끄고, 빈 응답은 성공이 아니라 실패로 처리하는 규칙을 세웠습니다.
- **자유 서술 칸은 JSON을 깨뜨린다.** 사유를 자유롭게 쓰게 하면 길이 제한에 잘려 형식이 깨졌습니다. 출력 스키마를
  엄격히 고정하고, 결론보다 사유를 먼저 쓰게 순서를 바꿨습니다(결론이 먼저 나오면 옳은 사유가 결론을 못 뒤집었음).
- **캐시 키에 들어가지 않은 것은 바뀌어도 모른다.** 모델명이 판정 캐시 키에 없으면 모델을 바꿔도 옛 판정이
  그대로 나옵니다. 비교 실험 전에 캐시 키부터 점검해야 합니다.
- **더 큰 모델이 병목을 풀지는 않는다.** 총 파라미터가 약 7배인 모델로 바꿔도 결과가 나아지지 않았고, 원인은 검색 단계에 있었습니다.

## 기술 스택

- **언어·서버**: Python 3.12 (API 서버 FastAPI·Docker Compose 배포는 팀원 담당)
- **모델 서빙**: Ollama (로컬 GPU 1대), 비교 실험에 vLLM
- **문서 처리**: PyMuPDF / pymupdf4llm (텍스트 PDF, OCR 미사용)
- **검색**: FAISS (bge-m3 벡터), BM25 하이브리드 실험, numpy
- **모델**: gemma4 26B-A4B (생성), KURE-v1 · bge-m3 (임베딩)
